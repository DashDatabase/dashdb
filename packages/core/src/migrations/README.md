# Migration generators

Turn a `DiffResult` (see `../diff`) into migration files.

| Function                                                | Output                                                                                                             |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `generateSQL(diff, dialect)`                            | `up` / `down` SQL, the `Statement`s behind them, and an `irreversible` count                                       |
| `generatePrismaMigration(diff, ir, { name })`           | `prisma/schema.prisma`, `prisma/migrations/<timestamp>_<name>/migration.sql` (+ `down.sql`), `migration_lock.toml` |
| `generateDrizzleMigration(diff, ir, { name, journal })` | `drizzle/schema.ts`, `drizzle/<NNNN>_<name>.sql` (+ `.down.sql`), `drizzle/meta/_journal.json`                     |
| `generateFileBundle({ diff, after, targets, name })`    | All of the above as `{ path, contents }[]` for zipping                                                             |

Every file starts with a header: generated by DashDB, timestamp, operations by kind, warning
count and irreversible count.

## Transactions

- **Postgres** (`generateSQL`): everything runs between `BEGIN` and `COMMIT`, except what
  Postgres refuses inside a transaction block. Those statements come before or after it, each
  with a comment: `DROP INDEX CONCURRENTLY` and `ALTER TYPE … ADD VALUE` before, and
  `CREATE INDEX CONCURRENTLY` after. Indexes are built concurrently only when they are
  non-unique and on tables that already exist (`concurrentIndexes: false` turns this off).
- **MySQL** has no transactional DDL. Each statement commits on its own, and the header says so.
- **Prisma and Drizzle** run each migration file inside their own transaction, so their SQL has no
  `BEGIN`/`COMMIT` and no `CONCURRENTLY`. Enum values added in such a migration cannot be used
  until it commits.

## Irreversible operations

Dropping a table or a column, and removing enum values, destroy data. The down migration
recreates the structure only. Both files mark these statements with `-- IRREVERSIBLE: …`, and
`SqlMigration.irreversible` counts them.

## Drizzle limitations

- No `meta/<NNNN>_snapshot.json` is written. It is drizzle-kit's private model of the schema;
  `drizzle-kit migrate` does not need it, but the next `drizzle-kit generate` diffs against
  the latest snapshot. If you mix DashDB migrations with `drizzle-kit generate`, run
  `drizzle-kit introspect` (or `generate` once) to resync.
- drizzle-kit has no down migrations. `<NNNN>_<name>.down.sql` is written for manual
  rollback, and the migrator ignores it.
- `meta/_journal.json` has no header comment: JSON has no comments, and drizzle-kit parses
  the file.

## Prisma limitations

- Prisma Migrate has no down migrations. `down.sql` sits next to `migration.sql` for manual
  rollback, and Prisma ignores it.
- `schema.prisma` is regenerated from the IR (`toPrisma`). Hand edits are not preserved.

## Not supported

SQLite: its `ALTER TABLE` covers few changes, and the rest need table rebuilds.
